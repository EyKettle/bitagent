# BitAgent 概念论述

一个**程序控制流程**的 Agent 应用：

控制流由普通代码掌握，LLM 从主导者降级为工具。LLM 只负责翻译——把自然语言转成机械可读的结构化数据
（以及把程序结果转回人类友好的表述），中间的一切决策都由忠实且逻辑确定的传统程序完成。

这与简单的传统 Agent 循环（模型决定下一步做什么）正好相反。详细理念见 [理念阐述章节](#理念阐述)。

## 核心哲学

<!--Not Ready-->

1. **行为上**，能用程序化流程解决的事情，绝不交给概率。
2. **交互上**，能用图形界面解决的事情，绝不用大量文字替代。
3. **权力上**，尊重用户的知情权和选择权，任何信息都能看到。

### 错误处理

出现问题优先报告给用户，无论是否阻塞。

每个问题都要至少说清楚“是谁有问题”、“有什么问题”、“什么原因导致的”。其他信息包含在信息卡片的其他部分。
使用图标和布局来优雅地展示信息，绝不用文本一刀切。

### 状态展示

所有状态都要有地方展示，通过分组、分层、增加页面来优化信息布局。不能以“信息太多”而忽略，这是对用户知情权的侵犯。

### 决策权力

即便是垃圾也不会替用户丢掉。用户可以选择让 LLM 处理，但并不等同于交给程序自动
让 LLM 处理。

## 概念解释

<!--Not Ready-->

### 活动代理 - Agent

每个 **活动代理** 是一个单独的，包含多个 **LLM 实体(Entity)** 的 BitAgent 实例。

### LLM 实体 - Entity

**LLM 实体** 对应传统 Agent 应用的 Subagent 概念。不同的是 **LLM 实体** 相当于一个
专门处理特定功能的函数。

每个 **LLM 实体** 都有专属的职责。根据职责分配不同的 **上下文片段** (身份、职责、规范、状态)
和工具集。工具集即传统的*工具调用(Function Calling)*能力，是 LLM 端与程序交互的重要支点，
LLM 与工具调用的关系相当于用户与 GUI 的关系。*工具调用*比*格式化输出*更具可控性和逻辑确定性。

所有 **LLM 实体** 由程序统一调度——派发任务，LLM 提交，结束；不需要主动等待——天然避免
主 Agent 反复等待子 Agent 工作，产生上下文垃圾（等待命令）的情况。

### 原子标签 - Flag

**原子标签** 是语义原子，每个语义只有一个原子标签对应。原子标签不是字符串，不与任何词汇做绑定，
它只代表某个概念的**逻辑原语**。

程序应大量使用 **原子标签** 来消除歧义。除非*必须使用字符串来避免信息失真*，否则应当一律
使用 **原子标签**。它本质是 `u32` 数据，会大幅增加性能。

#### 原子标签的职责

**原子标签** 是用于搜索/筛选/匹配的最佳基础。它具有身份唯一性，是逻辑确定的语义原语。所有数据类型
都应该采用 **原子标签** 来表述结构、类型和内容，以便具备机械可读性。

#### 原子标签的语义标签 - Label

为了 **原子标签** 可被人类辨识，程序会维护一张表单，标注每个 **原子标签**
持有的 **语义标签(Label)** 。这个表单可以被用户管理，程序和 LLM 会
根据 **语义标签** 来使用 **原子标签**。

**语义标签** 允许使用词组来避免歧义，但必须保持精简。

**语义标签** 不具有身份唯一性，可变动，只是用来展示。一次更新到处生效，
不用担心旧的 **语义标签** 和新的 **语义标签** 起冲突。

#### 原子标签的可变性

**原子标签** 只能由用户拟定，通过交互界面 (WebUI, GUI, TUI, CUI 等)
管理 **语义标签** 的表单。增删 **原子标签** 以及更改对应的 **语义标签**。

当超出当前的 **原子标签** 所能表示的范围时，**活动代理** 可以向用户发起增加和更新*标签表单*的请求。
用户可以在这个请求基础上做出自己的变更，也可以选择直接接受或拒绝。

但是，这是备用通道，不允许滥用。只有真正面临 **原子标签** 无法表达的时候才允许使用备用通道。

#### 原子标签储存方式

**原子标签** 以专属的 u32+u8 表储存在二进制文件 (`*.fglb`, 即 Flag Label 格式)。通过相关工具链进行变更。
每个表储存 **原子标签** 和对应的 **语义标签**，数据在对齐的情况下保持紧凑。

工程实践上至多存在两个 `*.fglb`（静态表和动态表），建议只有一个 `*.fglb`（原子标签的唯一事实来源）。
复杂的分类逻辑应该由程序实现，而不是文件代劳。

### 环境上下文 - Context

**环境上下文** 是 **活动代理(Agent)** 的唯一事实来源，是储存状态和数据的唯一载体。
**环境上下文** 相当于一个实例对它能接触到的一切所产生的认知。

**环境上下文** 统一事实来源，分层分类管理所有信息。大到系统提示词、临时记忆、结构化消息，
小到目录结构快照、文件内容快照、日期时间。**环境上下文** 中的标准、技能、文件快照等内容
都是副本，有关内容的本体在本地永久储存。

它提供统一的接口让程序其他部分（包含 **LLM 实体(Entity)**）安全且准确地处理信息更新。

除非*必须使用字符串来避免信息失真*，否则环境上下文的数据优先使用 **原子标签(Flag)**。

### 记忆

记忆分为多层内容，分别处理不同类型的经验。

#### 技能

**技能(Skill)** 是做一件事情的规范流程，是一份指南，附赠导向相关规范的索引和速查表。

每个技能只能指向一个课题，但可以包含多种 **流程**。针对不同工作类别遵循不同 **流程**。

#### 事实

发现的客观事实将记录在 **事实(Fact)** 表中，协助 LLM 澄清事实。

#### 标准

这是约束 LLM 行为的提示词，不同类别的系统提示词、不同身份的职责说明、
不同领域的规范说明就属于这类内容。

BitAgent 的系统提示词是模块化的。通过组合不同 **标准(Standard)**，
以最小文本量精准定位 LLM 行为和权力的边界。

系统提示词由 **环境上下文(Context)** 确定。

### 预测轨道 - Predict Tracks

根据用户的需求类型和叙述的清晰度，程序按照不同的思路拆解分析用户消息。

#### 预测轨道的职责

**预测轨道** 是思维骨架。它会锁定一套用户消息解析方式，同时产出*逻辑确定*的**意图数据**，
是决定是否选择以及选择什么 **流程(Flow)** 之前的必要经历。**预测轨道** 评判用户的需求类型
和叙述清晰度，决定 **环境上下文** 预先准备的信息(技能、标准、工作路径文档等)，决定每一步
思考的目标，和后续是否产生询问，以及决定询问的方向和目标。它的职责就是帮助 LLM 在概率中
寻找清晰的逻辑，理清用户的意图。**虽然它工作量小，但它很关键**。

#### 预先分析清晰度

在执行 **预测轨道** 前总是执行*飞行检查*，根据清晰度，决定使用的 **预测轨道**，
类似于 **流程** 的*大分支*。

#### 根据需求类型变更预测模式

如果用户只是*闲聊*，那么没必要进行深入推理，可以选择简单的轨道。如果用户是在*讨论*，
就需要深度的思考和探索精神，需要选择合适的长轨道。如果用户是在要求执行*任务*，
就需要提前分析行为边界，需要带有行为边界分析的轨道。

#### 预测轨道的退行路径

当不存在合适的 **预测轨道** 时，需要调用 **LLM 实体** 根据*预测轨道创建指南*现场
生成一条临时的轨道。再遵循临时轨道解析用户意图。

临时轨道在工作被用户确认完成后的收尾环节，需要与用户商讨如何吸收固化——建立为独立轨道，
合并到已有轨道或者直接拒绝选择更新已有轨道。

临时轨道会一直保留直到用户处理，程序不替用户选择丢弃。临时轨道总是在收尾环节向用户申请处理，
不会在其他环节打断工作。

#### 预测轨道的可变性

**预测轨道** 可以由用户拟定，也可以由 BitAgent 在总结经验时拟定。自学习的详细说明
见 [自学习章节](#自学习)。

### 流程 - Flow

**流程** 是工作的核心骨架。不是用来限定 LLM 活动的，而是主导 Agent 活动的。LLM 只是流程所需要的工具。

#### 流程的职责

**流程** 决定行为框架。通过复杂度决定步骤，步骤决定行动路径，每项步骤的限定条件和模式决定行动细节。

##### 预测检查

不是所有步骤都是一个工作中需要的，也不是所有步骤都应该完整执行。具体情况视复杂度决定，而不是死板追求流程完整。

每个流程开始必然面临一个 **预测检查** 环节，决定 **环境上下文** 预先准备的信息(需要额外加载的**标准(Standard)**、
工作路径的文档快照、外部文档快照、已知需要的代码文件快照等)，决定行动的复杂度和工作量，决定后续流程展开的步骤。
每个步骤都有*前置条件*和*精简门槛*：前置条件决定了这个步骤是否应该被执行，精简门槛决定了这个工作是否可以被简化或省略。

预测检查分为两层：

1. 程序化检查: 检查携带的 **原子标签(Flag)** 确定前置条件/精简门槛是否满足，自动决策
2. LLM 保底检查: 在进入特定步骤前，根据*程序化检查*的结果和*精简门槛*，做保底决策，避免无意义的工作

##### 流程模式

不同的 **流程模式** 会直接改变整个流程的**结构**。*流程模式选择*本身也是一个步骤。
每个 **流程** 第一步都是*流程模式选择*，但不代表着只有一个*流程模式选择*。在流程过程中仍然可以插入
*流程模式选择*的步骤，以切换到合适的分支流程，控制后续任务步骤的整体结构。

但这个**插入时机**不在运行期，而是**设计工作流程**的时候。流程一开始可以决定一个大分支，在之后可以决定一个小分支。
即大模式、小模式的区别。

#### 流程的可变性

**流程** 从属于特定 **技能**，可以由用户拟定，也可以由 BitAgent 在总结经验时拟定。自学习的详细说明
见 [自学习章节](#自学习)。

#### 流程的模板示例

一个标准的流程通常包含三部分(准备，工作，收尾)，六个环节：

1. **预备环节**: 为了达成目标、为了完美的达成目标，需要处理所有可以预先处理的事情，
   以官方和规范的资料锚定正确路径，预测之后的结果及应对措施
2. **工作环节**: 按照既有要求和规划，执行工作
3. **审查环节**: 自我审查工作结果的环节
4. **优化环节**: 调整工作结果，不断接近目标的环节。通常会再接上**审查环节**
5. **报告环节**: 将工作结果报告给用户的环节，此时是用户审查的阶段，和用户会讨论产生下一步规划，
   或决定结束工作
6. **收尾环节**: 有证据证明工作完整结束，且用户明确批准结束的情况下，完整所有收尾工作，
   处理所有状态的生命周期

**注意**：在真实的 **流程** 中，不会直接拿六个环节组成步骤。步骤和环节是两码事。一个环节可能包含多个步骤，
一个步骤可能属于多个环节。

## 理念阐述

### LLM 的职责

最适合 LLM 的职责只有以下两点：

1. **意图捕获**: 负责从自然语言中捕获用户意图
2. **转译处理**: 负责将意图翻译为准确的机械可读的计算机数据，或者将计算机数据转译为可读的自然语言

但是，在当前时代下，传统程序仍然无法自主做到逻辑推理，因此 LLM 仍需要肩负以下职责：

3. **撰写文本**: 根据意图和要求，编写文件内容、撰写回复与报告
4. **视察审核**: 根据意图和要求，对某些内容进行审查
5. **逻辑推理**: 根据条件和目标，产生猜测，推理验证，得出结论

这五条职责是 LLM 所需的最小职责也是最大职责。

### 程序的职责

传统程序最适合做已经被预测的事情。它能保证在运行时完全遵守预先拟定的逻辑，不会因为意外情况
或者随机想法而越界。

#### BitAgent 中的程序职责

在 BitAgent 中，程序的职责是：

1. **处理选择**: 通过 **预测轨道(PredictTracks)** ，完成意图归类，决定后续 **流程(Flow)**
2. **控制流程**: 通过预先拟定的 **流程(Flow)** 强制 LLM 忠实完成工作
3. **提供接口**: 为开发者和 LLM 提供对程序数据和功能进行变动的接口
4. **提供表单**: 为 LLM 提供速查表，提供一份官方事实来源

## 会话与历史

<!--Not Ready-->

BitAgent 的会话虽然仍采用时间轴顺序排列，但不使用传统的“对话与事件数据结构”，而是选择
可分层可自动化管理的**行为与状态数据结构**。

### 行为与状态数据结构

<!--Not Ready-->

BitAgent 的记录只关注三件事情：**用户**问了什么，**LLM** 回答了什么，**Agent** 做了什么。
即**行为记录**。

三件事可分层、可自动化管理。在上下文不足时，程序可以自行按照重要级别剔除细节或浓缩整类事件，
避免 LLM 压缩的不稳定性——丢失风险和信息失真。

状态记录即 **环境上下文(Context)**。完整的会话信息由*行为记录*和*状态记录*构成，即**行为与状态数据结构**。

### 会话与历史的未来设计

*会话与历史*在 BitAgent 的完整设计中根本不存在。BitAgent 是一个人物，记忆是一个整体，不应该按照对话记录
分割整个 BitAgent。

BitAgent 会按照*关键词*(使用**原子标签(Flag)**)构建 **记忆网络(MemWeb)**，
BitAgent 在需要的时候会展开部分记忆，不需要用户手动管理会话。这将从根本上避免用户新开对话
重述大量前置信息的问题。

这有一个缺陷：低智商的 LLM 会误牵连看似相关但不应关联的记忆。这点需要未来在程序逻辑中进行限定或寻求
一种完全自动化的方案。

### 会话启动的预加载

会话启动会**预加载**上下文数据来提前做准备。会话启动的预加载分两层：

1. **预测轨道** 开始时会预先筛选需要的**技能**、**标准**、工作路径信息等内容
2. **流程** 开始时会将真正和工作关联的**标准**、外部文档快照、工作路径信息、已知需要的工程文件快照等内容
   加载到 **环境上下文**

### MVP 阶段的形态

在 MVP 中，睡眠期/清醒期/活动期这些属于 **BitAgent 人格** 的概念都不存在。
MVP 阶段保持传统的“提需求 -> 做工作 -> 总结吸收”的线性自学习流程。

无论是在 MVP 还是未来计划中，都不存在后台进行的隐式吸收。未经用户决策的吸收存在豆腐渣风险。
无论用户是否真的选择审查，都要保留用户的审查能力，而不是替用户选择方便的路径而陷入豆腐渣风险中。

### 重载特性

所有变更都不会在活动中生效，只有工作完成才会进行刷新。刷新会同时作用于其他活跃会话，
不只有新会话会读取到新数据。

### **子代理(Subagent)** 是一等公民

<!--Not Ready-->

遵循 **单一职责原则** 可以极大地提升 LLM 的逻辑清晰度和工作效果。
每类工作所使用的 LLM 都是独立的子代理，拥有**专属的身份、职责和状态**。

但在 BitAgent 中，所有 LLM 实例都是子代理。为了和 **活动代理(Agent)** 区分，
所有 LLM 实例都称为 **LLM 实体(Entity)**。

处理总结信息，跟用户对话的也是一个 **LLM 实体**。
